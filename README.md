# Retroloop

Sprint retrospectives where the action items actually get done.

A real-time retrospective board for teams: everyone writes cards anonymously,
the cards are revealed, grouped and voted on, and the retro ends with a short
list of action items — each with an owner and a due date, carried into the next
retro until it is done. Participants join by link, no sign-up.

Why another retro tool: less than half of retrospective action items get
completed in most teams, and existing tools stop at the board. See
[docs/RESEARCH.md](docs/RESEARCH.md).

> Work in progress, built in small phases — see the commit history.

## Stack

| Part | Tech |
|---|---|
| Web app | Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS 4 |
| Realtime server | Node.js 24, Fastify 5, Socket.IO 4 |
| Data | PostgreSQL 18 + Prisma 7, Redis 8 |
| Shared contract | `@retro/shared` — socket events and payload schemas (zod), used by both sides |
| Tooling | npm workspaces, Vitest, ESLint, tsup, Docker Compose, GitHub Actions |

```
apps/web         Next.js app (UI)
apps/server      Fastify + Socket.IO realtime server, Prisma schema and migrations
packages/shared  Wire protocol shared by web and server
docs/            Research and design notes
```

The web app and the realtime server are separate processes: Next.js serves the UI,
the server keeps the WebSocket connections and owns the board state. Every event
that crosses the wire is declared once in `packages/shared`, so a change to the
protocol fails type-checking on both sides instead of at runtime.

## Getting started

Requires Node.js 22.12+ (24 recommended) and Docker.

```bash
cp .env.example .env
npm install
npm run db:up        # PostgreSQL on :5433, Redis on :6380
npm run db:migrate
npm run dev          # web on http://localhost:3001, server on http://localhost:4000
```

Start a retro on the home page, then open the invite link in another browser
(or a private window) to join as a second person.

`GET http://localhost:4000/health` reports each dependency and answers `503`
within a second if one of them is down.

## How the realtime part works

- **No accounts.** Joining a retro returns a secret token that the browser keeps;
  the server stores only its SHA-256 hash. Coming back with the token (a reload,
  a second tab) restores the same participant.
- **The server owns the state.** Clients apply their own changes optimistically and
  roll back if the server rejects them (for example, editing someone else's card).
- **No duplicates on retry.** Card ids are generated by the client, so a request
  resent after a dropped connection is recognised instead of stored twice.
- **Reconnects resync.** Every (re)connect re-joins the retro and replaces local
  state with the server's snapshot, so nothing missed while offline is lost.
- **Presence per socket.** A participant with two tabs open stays online until the
  last one closes.

## How a retro runs

| Stage | What happens | Enforced on the server |
|---|---|---|
| Write | Everyone adds cards | Other people's text is not sent to the browser at all — only a placeholder — so it can't be read in DevTools |
| Group | Cards are revealed; drag a card onto a similar one to group them | Groups are one level deep; deleting a group's top card promotes the next one |
| Vote | Everyone spends a limited number of votes on groups | The limit is checked in a transaction that locks the voter's row: 10 parallel votes with a limit of 3 store exactly 3. Totals stay hidden |
| Discuss | Groups ranked by votes; the facilitator highlights the current topic; the team agrees on action items | Vote totals are revealed only now. Every action item needs an owner and a due date, and there are at most three per retro — checked under a row lock, so parallel adds can't overshoot |
| Wrap up | What was agreed, the team's follow-through score, exports, the link to the next retro | |

## Follow-through: the part other retro tools skip

A team's retros form a series. When the facilitator starts the next retro, it
opens with a **review** of every action item still open from earlier ones: done,
not yet (with a new due date), or dropped. Items that are not done keep coming
back until they are; the review stage is skipped when nothing is open.

The **follow-through score** — the share of action items from earlier retros that
actually got done — is shown at the review and at the end of every retro. It is
also the product's success metric: most teams finish under half of their retro
action items (see [docs/RESEARCH.md](docs/RESEARCH.md)).

Agreed items leave the tool the way teams already work: **Markdown** for a wiki
or chat, **CSV** that Jira's importer maps without setup, a prefilled **GitHub
issue** link, and an **.ics** calendar event on the due date for the owner.

Whoever creates a retro gets a facilitator key (kept in their browser, stored as a
hash); only the facilitator moves between stages, runs the timer and can hand the
role over. Card authors are never sent to other participants in any stage — the
client only learns "mine" or "not mine". The timer runs on the server clock; each
browser corrects for its own clock offset, measured on join.

## Checks

```bash
npm run typecheck
npm run lint
npm test
npm run build
```

Server tests are integration tests: they start the real server and talk to it over
Socket.IO, against a separate `retro_test` PostgreSQL database (created and migrated
automatically, so `npm run db:up` must be running). CI runs the same steps on every
push against a fresh PostgreSQL.
